## コンセプト

「**今いる場所から、すぐ食べに行ける店を探す**」

余分な操作を減らし、現在地の取得 → 範囲選択 → 検索 → 結果閲覧までをシンプルな導線で完結させることを重視しました。

## 画面概要

### 1. 検索条件入力画面（SearchScreen）

現在地の取得ボタン、検索半径セレクター、キーワード入力フィールド、検索実行ボタンを配置した画面。現在地を取得してから検索できます。

### 2. 検索結果画面（ResultsScreen）

API から取得したレストランを `RestaurantCard` 一覧で表示する画面。スクロール末尾で次ページを自動取得します。検索結果が0件の場合は範囲拡大ダイアログを表示します。

### 3. 店舗詳細画面（DetailScreen）

選択した店舗の詳細情報（ヒーロー画像、ジャンル、予算、住所、アクセス、営業時間）を表示します。HotPepper の詳細ページへのリンクボタンも設置しています。

## 利用技術の選定理由

### Flutter / Dart を選定した理由

1つのコードベースで iOS / Android 両プラットフォームに対応できるため選択しました。今回の課題は UI の複雑さよりも API 連携・位置情報・状態管理の実装が中心であり、Flutter のホットリロードや Widget ベースの設計がプロトタイプの高速な反復に適していると判断しました。

### Claude AI（Claude Code）を利用技術として使用

コード生成・デバッグ支援・コードレビューに Claude AI（Claude Code CLI）を活用しました。生成されたコードはすべて自分で読解・検証し、動作確認を行った上で採用しています。特に以下の点で活用しました：

- `mounted` ガードの必要性など Flutter の非同期ライフサイクルに関する理解
- ネストされた JSON パースにおける型安全な typed cast（`as Map<String, dynamic>?`）の実装
- コードレビューによるバグ検出と修正方針の確認

## こだわったポイント

### 1. 検索結果0件時の検索範囲拡大ダイアログ

検索結果が0件だった場合、ユーザーを検索画面に戻すのではなく、アプリ側から次の検索範囲（例：300m → 500m）への拡大を提案するダイアログを表示するようにしました。ユーザーが手動で検索条件を変更する手間を省き、自然な導線でより広い範囲の再検索ができます。これは課題の要求仕様には含まれていない独自の UX 改善として実装しました。

### 2. 無限スクロールによるページング

`ScrollController` でスクロール位置を監視し、リスト末尾に近づいた時点で次のページを自動取得する実装を行いました。取得中はリスト末尾にスピナーを表示し、取得完了後にリストが継ぎ目なく続くようにしました。ページングは課題の要求仕様では optional とされていましたが、検索結果が多い場合のユーザー体験のために実装しました。

### 3. 店舗詳細画面のカスタムウィジェット設計

`DetailScreen` では `InfoRow`・`InfoChip` などの汎用カスタムウィジェットを定義しました。`Restaurant` モデルに新しいフィールドを追加した場合、`InfoRow(label: '...', value: widget.restaurant.xxx)` を1行追加するだけで詳細画面に反映できます。レイアウトやスタイルの重複を排除し、将来の機能拡張に対応しやすい構造にしました。

## デザイン面でこだわったポイント

- **カラーパレットの統一**：`AppTheme` でプライマリカラー・背景色・テキストカラーを一元管理し、全画面で一貫したデザインを実現しました
- **google_fonts（M PLUS Rounded 1c / Kaushan Script）**：アプリ全体のテキストに M PLUS Rounded 1c（日本語対応・丸みのあるフォント）を採用し可読性を高めました。AppBar タイトルには Kaushan Script（筆記体）を使用しブランド感を演出しました
- **カード型リスト**：`RestaurantCard` にサムネイル・店舗名・ジャンル・アクセスを収め、一覧での情報スキャンをしやすいレイアウトにしました
- **詳細画面のヒーロー画像**：`HeroPhoto` ウィジェットで画面上部に大きく画像を表示し、視覚的なインパクトを与えました

---

## 技術面でアドバイスして欲しいポイント

現在の実装では `setState` による状態管理をすべての画面で直接使用しています。`ResultsScreen` のような複数の非同期処理と UI 状態が絡み合う画面では、`isLoading` / `isLoadingMore` / `_error` / `_restaurants` といった状態が増えるにつれて管理が複雑になると感じました。

Riverpod や Bloc などの状態管理ライブラリへ移行することで可読性・テスタビリティが向上すると理解していますが、実務での適切な選定基準や移行タイミングについてアドバイスをいただけると幸いです。

## 自己評価

課題の要求仕様（検索条件入力・検索結果一覧・店舗詳細・GPS・ページング）はすべて実装できました。要求仕様に加えて、検索範囲の自動拡大提案や`mounted`ガードによるクラッシュセーフ設計など、実用品質を意識した実装も行えたと考えています。

一方、Flutter の経験が浅いため実装中に非同期処理のライフサイクル（`mounted`、`dispose`）やネストされた JSON パースで詰まる場面があり、状態管理の設計力やテスト実装は今後の課題として認識しています。また、テストコードが不足している点も改善が必要と自己評価しています。
